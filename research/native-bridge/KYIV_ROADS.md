# Київ: дорожній конвеєр і ресурси ПК, 2026-11-16

Виміряно оригінальний конвеєр EarthNG у грі, без підключення DLL до генератора.
Попередня робота моста прискорює експериментальний A*, а не дорожні меші. Тому
цей документ — базова лінія і набір даних для перенесення, не порівняння
готової Rust-побудови доріг із Lua.

## Ігровий цикл

Команда: `.venv\Scripts\python.exe earthng/test_world.py --out
out/native-bridge-road-route-20261116 --route out/routes/kyiv-center.json
--quality 50 --mod out/country-setup/earthng_ukraine.zip --planet
out/native-bridge-road-baseline-20261116/mod/earthng_planet.zip --probe --sample
--drive-seconds 20 --timeout 300`.

Перший тайл генератора готовий через 2,70 с від запиту, початкова ділянка з
дев'яти тайлів у знімку висадки — через 41,33 с; накопичений час шару `road`
генератора на той момент — 9,98 с. Це різні величини: час роботи Lua і час
очікування завантаження/рушія. Шар `road` у цьому генераторі містить не лише
чисту побудову дорожніх мешів. Виміряно 1,21 с у `tilesMs`, 3,06 с `queueMs`,
0,83 с `collisionMs` і 0,26 с `navMs` на тому самому зрізі; поля можуть
перекриватися або включати різні фази, їх не можна складати як незалежні.

Проїзд — 196,36 м, функціональна частина пройшла. Тест загалом позначений
`failed` через 9 кадрів понад 100 мс; p50 17 мс, p99 89 мс, найгірший
1101 мс. Це один запуск із холодним профілем і профілюванням. Кадр проїзду
показує дорогу та розмітку; візуальні зміни не вносилися. Пік приватної
пам'яті процесу — 7111 MiB, середнє завантаження головного процесу за весь
період 237% одного логічного ядра, пік 1426% за 250-мс вибірку. Це CPU усієї
гри, не лише генератора чи моста, не включає дочірні процеси CEF.

Перший запуск від 50.4477,30.5233 без контрольного маршруту не є успішним
проїздом: авто проїхало 9,90 м, помилки `not_moved` і `frame_over_100ms`.
Дані лишено в `out/native-bridge-road-baseline-20261116` для діагностики.

## Що потрібно для справжнього Rust A/B

1. Захопити точний список усіх клітинок, `tileRect`, прапорів якості, випадкових
   зерен, середовища, залежностей і дорожнього виходу саме з `native.buildTile`;
   одиночна offline-клітинка вище придатна лише як перший тест алгоритму.
2. Переносити конкретні CPU-етапи до Rust з перевіркою повних мешів,
   матеріалів, виходу навграфа, швів і маски зайнятості; не вважати A* на
   EGR1 побудовою доріг.
3. На ідентичній планеті/паку/маршруті порівняти Lua і міст: готовність до
   проїзду, реальний час до дороги попереду, CPU-потоки, пік RAM, створення
   рушієм, колізію, p50/p95/p99 і провали кадру. Перевірити кількість потоків
   під час самої їзди, а не лише на екрані вибору місця.
4. Міст потребує керованого пулу потоків і черги, обмежень пам'яті, скасування
   непотрібних тайлів, контролю життєвого циклу DLL та автентифікації IPC.
   Не завантажувати весь CPU автоматично: гра одночасно використовує фізику,
   рендеринг і завантаження даних.

## Масштабування моста на ядрах

Важливо: нижче навантаження A* по EGR1, **не генерація дорожньої геометрії**.
Сценарій `bench_scaling.lua`: граф 98 909 вузлів, 224 404 виділені дуги,
256 незалежних A* запитів, з них 240 досяжних, 12 повторень для кожної
кількості потоків і кожного з двох транспортів. Вартість і кількість обійдених
вузлів кожного результату звірено з Lua. Це синтетичні запити до реальних
київських доріг, не запис користувацьких маршрутів. Вимір після стабілізації
початкового завантаження, профіль `out/native-bridge-scaling-worker-cpu-20261116`.

Замість статичного поділу на суцільні частини `route.rs` використовує спільний
атомарний лічильник наступної задачі. Кожне завдання виконується одним потоком;
незалежні результати складаються назад у початковому порядку. Робочі потоки
створюються заново для кожного пакета, це ще не постійний пул.

| Потоки | Rust, медіана, мс | Сокет: повний цикл p50 / p95, мс | CPU робітників, середнє логічних ядер |
| ---: | ---: | ---: | ---: |
| 1 | 126,1 | 135,4 / 139,7 | 0,97 |
| 2 | 60,6 | 63,4 / 66,3 | 1,89 |
| 4 | 37,6 | 51,3 / 55,9 | 3,11 |
| 8 | 33,1 | 35,4 / 37,9 | 4,51 |
| 12 | 31,1 | 36,4 / 36,7 | 4,80 |
| 16 | 32,0 | 38,0 / 40,6 | 5,07 |

CPU робітників — сума Windows `GetThreadTimes` усіх Rust-потоків, поділена на
суму реального часу Rust-пакетів. Через крок системного лічильника приблизно
15,6 мс, короткий час життя потоків і лише 12 пакетів це **груба оцінка**,
особливо для 8–16 потоків, а не точний замір кожного ядра. Окремий `monitor.py`
опитує CPU й пам'ять усього процесу гри раз на 100 мс; наприклад, фаза сокета
з 8 потоками має всього 4 вибірки й середнє 5,7 логічного ядра для всієї гри.
Неможливо надійно вирахувати чисту частку моста з цих вибірок. Пік приватної
пам'яті всього процесу у фазах сокета близько 3,75 GiB; це не пам'ять DLL.

Lua-еталон для тих самих 256 запитів: 327,1 / 307,9 / 308,4 мс. При 8 потоках
пакет обчислювався швидше, але повний час Lua й Rust не включає первинну
побудову графа; Rust-час включає старт потоків, повний час IPC — кадрове
опитування й перевірку результатів. У Lua еталон виконувався без штатних
поступок кадру. Фіксований порядок, один запуск гри, лише 12 вибірок, p95
оцінює практично другу найгіршу. Тому це ознака насичення конкретної задачі
після ~8 потоків, а не універсальний оптимум.

Для порівняння, до спільної черги окремий стабілізований прогін зі статичними
частинами дав Rust-медіани 107,8 / 64,8 / 42,3 / 31,4 / 30,0 / 31,3 мс для
1/2/4/8/12/16 потоків; після переходу на чергу окремий прогін дав
115,4 / 54,2 / 33,2 / 28,5 / 28,2 / 28,9 мс. Це різні запуски, а не
рандомізоване A/B; причину розбіжності та виграш черги треба перевіряти
повтореннями. Ранній запуск `out/native-bridge-scaling256-20261116` забруднений
фоновим завантаженням гри: у фазі 2 потоків процес коротко зайняв 14,47
логічного ядра, а RAM зросла з ~2,5 до ~3,6 GiB. Його не використовувати як
оцінку моста.

Артефакти: `out/native-bridge-scaling-worker-cpu-20261116/summary.json`,
`cpu.jsonl`, `user/current/e2r_bridge/bench-scaling.json` і попередні профілі.
`summarize_scaling.py <out/run>` відтворює агрегати. Для кращого наступного
замірювання потрібен довгоживучий пул із замірами накопиченого CPU на потоках,
A/B у чергованому порядку, достатньо довгі фази, фоновий CPU за ядрами,
перевірка пам'яті до й після, одночасний дорожній стримінг і фізичний проїзд.
