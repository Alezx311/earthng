# Rust у нативному моді: дослідження 2026-11-09

Гілка `exp/rust-in-mod`. Питання: чи можна прискорити роботу карти в самій грі кодом на Rust, без
стороннього сервера і без підміни DLL. Якщо в моді ніяк, то яку частину логіки перенести в збирач паків.

Гра BeamNG.drive 0.40.5.0.302427, LuaJIT 2.1.1788767029, ізольований профіль `test_world.py --probe`,
пак України, висадка в центрі Києва (50.4477, 30.5233), якість 50, графіка Normal 1280×720.
Проби лежать у [`research/rust-in-mod/`](../research/rust-in-mod).

## Коротко

- **Рідний код Rust у моді неможливий.** Пісочниця GE Lua забороняє `ffi.load` і `package.loadlib`
  («sandbox: ffi.load denied») і не пускає вказівникові типи. Отже, своєї DLL не завантажити навіть
  чесно, без підміни.
- **Rust → WebAssembly у CEF-інтерфейсі теж неможливий.** Рендерер CEF запущено з
  `--js-flags="--jitless"`: `WebAssembly` не визначено, JS виконується інтерпретатором (у 6 разів
  повільніше за LuaJIT), а воркери заборонені CSP `worker-src 'none'`.
- **Що працює: LuaJIT FFI як шар даних.** Масиви й структури `ffi.new` і `ffi.copy` з рядка в
  `uint32_t[]`/`float[]`/структуру — це один memcpy. Rust-збирач може писати дані у формі, яку гра
  копіює одним викликом, а не розбирає побайтово.
- **Прототип формату `EGB3`** (u32 замість varint після таблиці рядків) на справжніх клітинках Києва:
  декодування в **2,0–2,7 раза швидше**, таблиці на виході **ідентичні** нинішнім. Сміття з кешем
  клітинки не більше, ніж зараз. ZIP пака більший на 22–24 % у місті і на 46–53 % у полі.
- Читання клітинок займає **20–26 % усієї генерації** на висадці в центрі Києва (7–11 с із 34–41 с).
  Найближчий реальний виграш від Rust — саме тут: збирач пише формат, який Lua не розбирає.

## Що дозволяє пісочниця гри

Замір пробою `p1_sandbox.lua` / `p3_ffi_worker.lua` у запущеній грі.

| Можливість | Результат |
| --- | --- |
| `require('ffi')` | є |
| `ffi.load('kernel32')`, `package.loadlib` | `sandbox: ffi.load denied`; `package.cpath` порожній |
| `ffi.cdef` функції, `ffi.C.<своя функція>` | `invalid C type` (лише ті `ffi.C.BNG_*`, що відкрила гра) |
| вказівникові типи (`void*`, `uint32_t*`), арифметика `масив + n` | `invalid C type` |
| `ffi.cast('uint32_t*', x)` | повертає `x` без змін (тому «`ffi.cast` нічого не робить» у [PERFORMANCE.md](PERFORMANCE.md)) |
| `union` | `invalid C type` |
| `ffi.new('float[?]', n)`, масиви структур `struct {float x, y, z; uint16_t kind, flags;}` | працює |
| `ffi.copy(масив, рядок, n)` у `float[]`, `uint32_t[]`, `int16_t[]`, структуру | працює, байти little-endian читаються як є |
| `ffi.string(масив, n)` | працює (лише від початку масиву) |
| `string.buffer` | є, але `buf:ref()` дає `uint64_t`, не вказівник: без користі |
| `table.new`, `table.clear`, `jit.opt`, `jit.profile` | є |
| 1 млн чисел | `float[?]` — 3,9 МБ одним об'єктом; таблиця — 8,2 МБ |
| `io.open` | шлях у VFS (ZIP модів і тека користувача), запис лише в теку користувача |

`ProceduralMesh:createMesh` приймає вершини як таблиці `{x=, y=, z=}` або `vec3` (cdata). FFI-масив
`float[]` мовчки дає порожній меш. Тобто вихід у рушій лишається Lua-таблицями. Це не вузьке місце:
таблиця вершини коштує ~0,09 мкс, а сам `createMesh` — ~1,1 мкс на вершину (20 тис. трикутників за 65 мс).

11.11 (`p20_mesh_cdata.lua`): `createMesh` читає за іменами полів і грані-структури `{int32 v, n, u}`,
і UV-структури `{float|double u, v}`. Масив `{0, 2, 1}` замість грані не підходить, `vec3` на місці UV
— теж («немає поля v»). Розміри в грі: вершина-таблиця 170 Б, `vec3` 50 Б; грань 170 / 38 Б; UV
122 / 42 Б. Генератор тепер віддає вихід саме так ([PERFORMANCE.md](PERFORMANCE.md), «Сміття
генератора»). Збирачу це не шкодить (`p21_cdata_gc.lua`): мільйон cdata збирається так само або
швидше, ніж мільйон таблиць.

## Що дозволяє CEF (інтерфейс гри)

Проба `p2_cef.lua`: JS через `be:executeJS`, відповідь назад через `window.beamng.sendEngineLua`.

| Можливість | Результат |
| --- | --- |
| `WebAssembly` | не визначено (рендерер `--js-flags="--jitless"`) |
| JIT JS | немає: 10⁸ ітерацій простого циклу — 2190 мс; той самий цикл у LuaJIT — 370 мс |
| `Worker` з blob і з файлу `local://local/...` | заблоковано CSP `worker-src 'none'` |
| `SharedArrayBuffer`, `crossOriginIsolated` | немає |
| `fetch` файлів модів (`/earthng/countries/.../blocks/*.bin`) | працює, 1–2 мс на 17 КБ |
| ядер (`hardwareConcurrency`) | 16, але без воркерів їх не використати |

CEF — окремий процес, і паралельність там була б справжня. Але без WASM, JIT і воркерів обчислення там
повільніші за LuaJIT у головному потоці, а результат однаково треба перетворити на Lua-таблиці через
рядок із кодом Lua.

## Чого не варто пробувати

- **Rust → WASM → Lua** (транспіляція в Lua-код із лінійною пам'яттю). Лінійна пам'ять потребує
  читання `i32`/`f32` за довільним зсувом. Без вказівників, `ffi.cast` і `union` кожне читання
  перетворюється на збирання байтів через `bit`, що повільніше за рукописний Lua.
- **Обчислення в Lua автомобіля.** Його VM частково паралельна кадру, але кадр її чекає
  ([PERFORMANCE.md](PERFORMANCE.md), «Багатоядерність»): вікно перекриття лише 3–10 мс, і передача
  результату знову йде через таблиці GE.
- **Своя DLL через `ffi.C.LoadLibraryA`.** Технічно `ffi.C` бачить kernel32, але `cdef` функцій
  заборонено. Це й так обхід пісочниці, а користувач виключив DLL.

## Прототип EGB3: Rust пише, LuaJIT копіює

У клітинці v2 після таблиці рядків ідуть самі varint. EGB3 залишає таблицю рядків байт у байт, а далі
пише кількість значень (u32 LE) і кожне значення як u32 LE у тому ж порядку (зигзаг там, де він був).
Lua-декодер іде клітинкою точно так, як `cellformat.cell`, і будує ті самі таблиці. Змінюється тільки
`u()`: замість побайтового циклу — `vals[i]` з `uint32_t[]`, який заповнив один `ffi.copy`.

- Rust: [`rust/crates/pack/src/fixed.rs`](../rust/crates/pack/src/fixed.rs) (`transcode_block`,
  тест), приклад `cargo run --release -p pack --example egb3 -- <v2 блок> <v3 блок>`. Блок 16 МБ
  транскодується за 43 мс.
- Lua: [`research/rust-in-mod/cellformat3.lua`](../research/rust-in-mod/cellformat3.lua) генерує
  [`make_v3.py`](../research/rust-in-mod/make_v3.py) з `cellformat.cell`, щоб логіка не розійшлася.
  У гру прототип не підключено.
- Замір: [`bench_v3.lua`](../research/rust-in-mod/bench_v3.lua) через `earthng/probe.py`.

### Заміри в грі

Фільтр тайла `keep = {0, 0, 500, 500}`, як у грі (тайл бере чверть клітинки). Найкращий із двох
прогонів, GC на час заміру зупинено, «МБ» — приріст купи (сміття). «Тепла» — u32-масив клітинки вже
скопійовано (так клітинку читають чотири тайли, якщо масив кешувати). Таблиці v2 і v3 порівняно
поелементно: **однакові в усіх вибірках**.

| Вибірка (Україна) | Клітинок | v2, мс | v3, мс | v3 тепла, мс | v2, МБ | v3, МБ | v3 тепла, МБ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| центр Києва `e0300-n500 -3_-1`, 1–16 | 16 | 253–255 | 99–124 | 123 | 19,1 | 31,0 | 18,9 |
| центр Києва `-3_-1`, 17–32 | 16 | 320 | 122 | 153 | 23,3 | 38,8 | 23,2 |
| Київ `-2_-2`, 1–16 | 16 | 51 | 20 | 28 | 4,8 | 7,3 | 4,8 |
| поле `e0300-n500 3_3` | 64 | 18,9 | 7,0 | 7,9 | 2,7 | 4,0 | 2,8 |
| захід `e0240-n490 0_0` | 64 | 38,4 | 15,5 | 20,1 | 6,1 | 8,2 | 6,1 |
| захід `0_0`, без фільтра | 64 | 41,8 | 18,6 | — | 8,5 | 10,7 | — |

Прогони «тепла» йшли пізніше, і там уже був перезавантажений модуль, а гра стрімила в тлі. Тому тепла
не швидша за холодну: копія коштує мало, різниця між ними — розкид заміру. Кеш прибирає саме сміття:
холодний v3 копіює u32-частину клітинки через `sub()` у рядок, а потім у масив.

На 24 клітинках без фільтра (`p4_cells.lua`) видно, куди йде час v2. Розбір 475 тис. точок разом із
тегами — 474 мс і 100 МБ сміття. Ті самі точки, скопійовані `ffi.copy` у `float[]`, — 1 мс, а з
побудовою таблиць `{x, y, z}` — 43 мс і 56 МБ. Отже, після EGB3 залишається вартість самих таблиць, які
споживає генератор, а не формат.

## EGB3 у паках (11.11)

Крок 1 нижче зроблено в остаточному вигляді ([NATIVE_MODS.md](NATIVE_MODS.md), «Блок `EGB3`»), і він
**у грі нічого відчутного не дав**: висадка в центрі Києва з паком EGB3 — 32,0 с, з тим самим паком
у v2 — 32,1 с; генератор до готовності 7,17 с проти 7,29 с (`out/egb-02`, `out/egb-04`, BeamNG 0.40.5,
пак Київської області). Тож паки й далі пишуться у v2, а `EARTHNG_CELLS_V3=1` вмикає EGB3. Читання
EGB3 лишилось у грі, Python і Rust. Оцінка «20–26 % генерації» нижче («Де це в генерації») виявилась
хибною: стадії «… after start» містять не лише розбір клітинок. Офлайн розбір клітинок центру Києва
з v2 — ~2 с на 256 клітинок, а тайл читає чверть клітинки.

- **Слова u16 замість u32.** Число до `0xfffe` — одне слово, більше — `0xffff` і дві половини
  (2,9 % чисел у паку Київської області). Сітка висот — u16 дециметри над найнижчою точкою
  клітинки, окремим хвостом. Пак області після deflate: v2 224,6 МБ блоків, u32 306,7 МБ (×1,37),
  u16 261,9 МБ (×1,17). ZIP цілком 256,4 → 293,6 МБ, збирання 227 → 230 с.
- **Пише Python** (`country_format.transcode_cell` у `build_country._pack`, numpy, ~17 с на весь пак
  поодинці), Rust `fixed.rs` дає ті самі байти (перевірено на 14 блоках). Читають обидва формати
  Python (`decode_cell`, `decode_roads` перетворюють клітинку назад у v2), Rust (`decode_block`,
  `decode_roads`: маршрутизація читає зібраний пак) і гра. Туди й назад — байт у байт на всіх 39 596
  клітинках пака.
- **Гра.** `cellformat.lua` копіює слова й сітку в `uint16_t[]` одним `ffi.copy` і кладе масив слів
  у спільну сітку клітинки (її читають чотири тайли). Без FFI слова читаються `string.byte`.

Пастка, на якій перший варіант декодера дав лише 7 %: обхід об'єктів клітинки викликає читач чисел
`u` як upvalue. Коли `u` перепризначався з varint-читача на читач слів посеред клітинки, або коли одна
функція обходу отримувала обидва читачі, траси LuaJIT лишались прив'язаними до першого. Тепер обхід
(`features`) не має upvalue, а EGB3 отримує власну копію його байткоду (`load(string.dump(...))`).
Чотири найбільші блоки центру Києва (256 клітинок, фільтр чверті клітинки, як у тайла, lupa LuaJIT):

| Варіант | v2, мс | EGB3, мс | Сміття v2 → EGB3 |
| --- | ---: | ---: | --- |
| `u` перепризначається | 2219 | 2073 (×1,07) | 202 → 268 МБ |
| окремі стани Lua для кожного формату | 2145 | 500 (×4,3) | |
| остаточно: своя копія обходу, обидва формати в одному стані | 1601 | 551 (×2,9) | 200 → 269 МБ |

Сміття EGB3 більше на копію слів, тому масив слів кешується разом із сіткою. Потоковий бенч
(`bench_native.py --skip-tiles --budget 60`, центр Києва) готовий на 178–183 кадрі замість 188–190:
решта генерації читання клітинок не містить. Те саме показала гра.

## Наступні кроки

Порядок за виграшем і ризиком. Кожен крок не ламає старі паки й BeamNG 0.39: декодер обирає формат за
магічними байтами блока (`EGB2` / `EGB3`), FFI-масиви були в 0.39 так само.

1. ~~**EGB3 у пак.**~~ Зроблено й вимкнено за замовчуванням, див. вище. Має сенс разом із кроком 4:
   коли генератор братиме масиви замість таблиць, розбір стане помітною часткою.
2. **Сітка висот і `cellformat.terrain` через FFI.** Горизонт і далеке кільце читають самі сітки:
   `int16_t[]` замість таблиці з 66 тис. чисел (8 байтів на число) — менше купи для GC.
3. **Чисті функції від даних пака — у збирач.** Те, що генератор щоразу рахує з самих фактів OSM, не
   залежить від якості й кадру. Кандидати: `low` клітинки, суміжність стін будівель (`BLD.cover`),
   тріангуляції контурів (`triangulate`). Спершу заміряти їхню частку в грі (таймер навколо функції
   через пробу). Межа з [AGENTS.md](../AGENTS.md): пак тримає факти, не готове місто, тож без мешів і
   без статичного експорту.
4. **Генератор на масивах замість таблиць точок.** Найбільший можливий виграш для GC (точки стають
   одним cdata-об'єктом, і GC не обходить їх поштучно), але це переписування 13 тис. рядків
   `generator.lua`. Має сенс тільки після кроків 1–2 і з вузьких місць, які покаже профіль.
